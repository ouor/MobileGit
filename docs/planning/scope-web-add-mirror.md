# 범위 검토: 웹 화면에서 미러 등록

- 작성: PM
- 상태: **사용자 승인 대기**. 사용자 규칙의 1단계(재설계 판단)와 2단계(변경 범위)까지만 다룬다. PRD 수정과 구현은 승인 뒤에 한다.
- 요청: 앱뿐 아니라 웹 화면에서도 GitHub·GitLab 링크를 붙여 넣어 미러를 등록할 수 있게 해 달라.
- 읽은 것:
  - `docs/core/spec.md` (F-03, F-06, 3장 웹 API, 4장 보안 헤더, 8장 R2-06)
  - `core/GitServer.kt` (라우팅, `authorize`)
  - `core/Auth.kt` (`Authenticator.decide`)
  - `core/Sync.kt` (`MirrorController`)
  - `core/Credentials.kt` (`forUrl`)
  - `app/Core.kt` (연결)
  - `web/src/lib/api.ts`
  - PRD F-18, 7장, 9장, 11장

---

## 1. 결론

**부분 변경.** 전체 재설계는 필요 없다. 다만 단순히 "추가만" 하면 되는 일도 아니다. 이유는 두 가지다.

- **확정 결정 하나를 바꿔야 한다.** "웹은 읽기 전용"(F-18 AC3, AC9, 7장 제목과 원칙, spec 3장 제목)이다. 웹에 처음으로 쓰기 동작이 생긴다.
- **보안 경계를 새로 그어야 한다.** 웹 API가 GET만 있다는 전제 위에 서 있던 것들이다.
  - 인증: 쓰기 요청의 분류
  - CSRF 방어: 지금은 없다
  - 원격 접근: 폰이 사용자가 준 URL로 나가는 요청

반대로 미러 등록 로직(`MirrorController`)은 순수 Kotlin이라 앱과 웹이 그대로 같이 쓸 수 있다. CSP도 바꿀 것이 없다.

## 2. 재설계 판단 (항목별)

| 항목 | 지금 | 바뀌는가 | 정도 |
|---|---|---|---|
| "웹은 읽기 전용" 확정 결정 | F-18 AC3 "수정, 생성, 삭제, 업데이트 제공 안 함". 7장 "웹 화면 (읽기 전용)". 9장에는 별도 항목 없음. 11장 결정표에도 없음 | 바뀜 | **결정 변경.** "읽기 전용, 단 미러 추가 하나만 예외"로 고친다. 예외를 하나로 못 박아 삭제·설정·업데이트 같은 다른 쓰기가 따라 들어오지 않게 한다 (4장 범위 밖). 미러 자체의 읽기 전용(F-08, D-10)과는 관계없다. 미러는 등록 뒤에도 push를 받지 않는다. |
| 웹 API (GET만인가) | 그렇다. `GitServer`의 `/api/v1/{...}`는 `get(...)` 하나뿐이다. POST는 git 경로(upload-pack, receive-pack, LFS 안내)에만 있다 | 바뀜 | **추가.** 웹 API의 첫 POST 경로 두 개(확인, 등록)를 더한다. 기존 GET은 그대로 둔다. 다만 `GitServer`는 지금 `MirrorController`를 모른다. 생성자에 주입을 하나 더해야 한다 (`app/Core.kt`에서 `mirrors`가 `gitServer`보다 먼저 만들어지므로 순서 문제는 없다). |
| 인증 경계 | `Authenticator.decide(..., isPush, viaNgrok, anonymousOk)`. 웹 요청은 모두 `isPush=false`, `AccessAction.WEB`로 읽기 취급한다. 세 단계 규칙: 읽기·쓰기는 모두 비밀번호, push만은 읽기 익명, 끄기는 모두 익명. ngrok 경로도 같은 규칙(R2-06) | 바뀜 | **부분 변경.** 웹 등록을 "쓰기"로 분류하는 새 동작 종류가 필요하다. 지금 코드에서 쓰기는 push뿐이다. 권장은 "push와 같은 규칙"(결정 D-1)이다. 그러면 `decide(isPush = true)`를 재사용할 수 있어 인증 코드는 거의 바뀌지 않는다. ngrok 경로를 따로 다룰지는 결정 D-2다. 접속 기록에는 새 동작 값(예: `MIRROR_ADD`)이 하나 생긴다. |
| CSRF | 없다. GET만 있고, Basic 인증은 브라우저가 자동으로 붙이므로 지금까지는 문제가 아니었다 | 바뀜 | **새로 추가 (필수).** 사용자가 PC 브라우저로 폰에 로그인한 상태라면, 다른 사이트가 `http://192.168.x.x:8080/api/v1/...`로 폼 POST를 보낼 때 브라우저가 Basic 자격 증명을 실어 보낸다. 방어는 셋을 모두 건다. ① 요청 본문은 `application/json`만 받는다 (교차 출처면 사전 요청이 생기고, 서버는 CORS 허용을 내주지 않으므로 막힌다). ② `Origin` 헤더가 있으면 요청 Host와 같은 출처여야 한다. `Sec-Fetch-Site`가 있으면 `same-origin`이어야 한다. ③ Host가 직접 주소(IP, `localhost`, `.local`, `.ts.net`, 지금 연결된 ngrok 공개 호스트)여야 한다. ③은 DNS 리바인딩을 막는다. 익명 판정에서 이미 쓰는 `NetClassifier.isDirectHost`를 재사용한다. |
| CSP | 웹 UI: `default-src 'self'; script-src 'self'; ... connect-src 'self'; frame-ancestors 'none'`. raw: `sandbox` | 안 바뀜 | **변경 없음.** 같은 출처 `fetch`(POST 포함)는 `connect-src 'self'`로 이미 허용된다. 입력 폼은 번들된 JS로 만들므로 인라인 스크립트도 필요 없다. 클릭재킹은 `frame-ancestors 'none'`이 이미 막는다. |
| 등록 흐름 공유 (probe → 등록 → 첫 받기) | `MirrorController.preview(input)`(순수), `probe(url, credentialId)`(네트워크, 최대 120초 제한), `add(url, name, credentialId, …)`(레포 생성 + WorkManager로 첫 받기 예약, 예외 `INVALID_NAME`/`NAME_TAKEN`/`ALREADY_MIRRORED`/`STORAGE_LOW`) | 공유 가능 | **추가만.** 세 함수를 웹 API에서 그대로 부른다. 정규화, 중복 검사, 이름 규칙, 저장 공간 하한, 첫 받기, 보존 정책이 앱과 똑같이 적용된다. 웹 쪽에 같은 로직을 다시 만들지 않는다. 남는 일은 두 가지다. (a) `probe`는 오래 걸리는 네트워크 호출이다. 웹 요청에서는 짧은 제한 시간과 동시 실행 상한을 둔다 (지금 무거운 웹 요청용 `heavySlots`와 같은 방식). (b) 웹 API는 "업데이트 중" 상태를 모른다 (spec WR-6: 웹은 `progress=null`). 등록 뒤 첫 받기 진행을 웹에 보여 주려면 코어의 `coordinator.running`을 웹 응답에 내보내는 작은 추가가 필요하다. |

## 3. 변경 범위 (담당별)

### 3.1 코어
- `GitServer`에 `MirrorController` 주입과 POST 경로 2개를 추가한다. 경로 이름은 코어가 정한다. 예:
  - `POST /api/v1/mirrors/preview`: 입력 → 정규화 URL, 제안 이름, 이미 미러됨 여부, 접근 확인 결과(`Reachable(refCount, defaultBranch, pullRefCount)` / 토큰 필요 / 없음 / 실패)
  - `POST /api/v1/mirrors`: URL, 이름 → 만든 레포 요약, 또는 오류 코드 (`INVALID_NAME`, `NAME_TAKEN`, `ALREADY_MIRRORED`, `STORAGE_LOW`, `UNSUPPORTED_URL`)
- 인증: 두 경로는 쓰기로 분류한다 (D-1). ngrok 경로 처리는 D-2를 따른다.
- CSRF 방어 ①②③ (2장). 실패하면 403과 오류 코드를 준다.
- 원격 접근 제한 (D-5): 웹에서 받은 URL은 https만 허용할지 정한다. 토큰 사용 규칙은 D-3을 따른다. `CredentialStore.forUrl`은 지금 그 호스트의 첫 토큰을 자동으로 고른다. 그래서 웹 경로에서 토큰을 쓸지 말지를 코어가 명시적으로 넘겨야 한다.
- `probe` 제한 시간(예: 20초)과 동시 실행 상한(예: 1~2개)을 둔다. 넘치면 503 `BUSY`로 답한다 (기존 코드).
- 웹 레포 요약에 "첫 받기 중/업데이트 중" 상태를 더한다 (2장 (b)).
- 접속 기록에 새 동작 값을 더한다. 결과(성공/거부 사유)를 남긴다.
- spec 3장 제목과 설명("읽기 전용")을 고치고, 새 경로·오류 코드·CSRF 규칙을 적는다.

### 3.2 웹
- 레포 목록(W-01) 상단에 "미러 추가" 버튼을 두고, 입력 화면(새 W-06 또는 대화상자)을 만든다.
  - 붙여넣기 → 확인 결과 표시(정규화 주소, 받는 범위 "브랜치·태그 N개 · PR 브랜치 제외 · LFS·서브모듈 제외", 이미 미러됨이면 그 레포로 링크) → 이름 확인·수정 → 등록
- 오류 문구: 토큰 필요("앱에서 토큰을 등록한 뒤 다시 시도하세요"), 원본 없음, 공간 부족, 이름 충돌, 외부 공개 경로에서 거부(D-2를 거부로 정할 때)
- 등록 뒤에는 그 레포 홈으로 이동한다. 첫 받기가 끝나기 전에는 "받는 중" 상태와 빈 레포 안내를 보여 주고, 주기적으로 다시 읽는다.
- 모든 POST는 `Content-Type: application/json`으로 보낸다 (CSRF ①).
- 문구: 헤더의 "웹에서는 보기만 할 수 있어요"를 "웹에서는 보기와 미러 추가만 할 수 있어요"로 바꾼다.
- 정적 파일, 라우팅, CSP는 그대로 둔다.

### 3.3 안드로이드 UI
- 접속 기록 화면(A-13)에 새 동작 값의 표시 문구를 더하고, 필터 대상에 넣는다.
- 웹에서 만든 미러는 `repos` Flow로 메인 목록에 바로 나타난다. 화면 추가는 없다.
- 레포 상세의 생성 경로 표시에 "웹에서 추가"를 더한다 (`CreatedBy` 값이 새로 생기는 경우).
- D-2에서 별도 설정 스위치를 두기로 하면 설정 화면에 한 줄이 늘어난다 (권장안은 스위치 없음).

### 3.4 문서
- PRD (승인 뒤에 수정):
  - F-18 AC3·AC9와 7장 제목·원칙을 "미러 추가 하나만 예외"로 고친다.
  - 새 기능 ID를 붙이거나 F-06의 AC로 추가한다.
  - W-06 화면을 추가하고 5장 추적표를 고친다.
  - 11장에 결정을 추가하고, 6.6 AccessLog의 action에 새 값을 더한다.
- `docs/core/spec.md` 3장, `docs/web/` 진행 기록.

### 3.5 테스트
- 코어 단위 테스트:
  - 인증 단계별 허용·거부: 세 단계 × LAN/ngrok × 비밀번호 있음/없음
  - CSRF: `Content-Type`이 form/text이면 거부, 교차 `Origin`이면 거부, 직접 주소가 아닌 Host면 거부
  - 오류 코드 매핑
  - http URL 거부(D-5)
  - 토큰 사용 규칙(D-3)
- 웹 단위 테스트: 입력 → 확인 → 등록 상태 전이, 오류 문구.
- QA 실기기:
  - PC 브라우저에서 공개 GitHub 주소를 등록하고, 첫 받기를 거쳐 웹에서 둘러보고 앱 목록에 나타나는지 확인한다.
  - 이미 미러된 주소, 공간 하한, 비공개 주소를 확인한다.
  - 다른 출처 페이지의 폼 POST와 fetch가 막히는지 확인한다 (CSRF 시험 페이지).
  - ngrok 경로를 확인한다.
  - **앱이 백그라운드에 있을 때 첫 받기가 바로 시작되는지 확인한다** (5장 위험 1).

### 3.6 바뀌지 않는 것
- 미러 읽기 전용(F-08), 보존(F-11), 정규화·중복·이름 규칙(F-06), 저장 공간 하한, 첫 받기 방식(전체 미러)
- git smart HTTP 경로와 push 규칙, 기존 GET API와 응답 형식
- CSP와 보안 헤더, 정적 파일 제공 방식
- 앱의 미러 추가 화면과 공유 시트 흐름
- 인증 세 단계의 의미와 R2-06(ngrok에서도 사용자 설정을 따름)

### 3.7 이번에 넣지 않을 것
| 항목 | 이유 |
|---|---|
| 웹에서 삭제, 분리, 업데이트·확인 실행 | 되돌릴 수 없거나 원격에 부하를 주는 쓰기다. "미러 추가 하나만 예외"를 지킨다. |
| 웹에서 설정 변경(비밀번호, ngrok, 주기 등) | 보안 경계 자체를 바꾸는 동작이라 폰에서만 한다. |
| 웹에서 토큰 입력 | D-3 권장안. 평문 HTTP로 토큰이 지나가고, 토큰 관리 화면이 둘로 갈라진다. |
| 계정·조직 일괄 미러 | D-4 권장안. 원격 API 목록, 레이트리밋 대기, 일괄 진행 화면까지 웹에 옮겨야 해서 작업량이 두 배가 넘는다. |
| 여러 줄 URL 일괄 등록 | D-4 권장안. 코어 `addMany`는 있지만 웹에 일괄 진행 화면이 필요하다. 한 개씩 등록으로 시작한다. |
| PR 브랜치 포함 같은 고급 옵션 | 전역 기본값을 따른다. 바꾸려면 앱에서 한다. |
| 웹에서 빈 레포 만들기 | 요청 범위 밖이다. PC에서는 push로 만들 수 있다 (F-13). |

## 4. 사용자가 정해야 할 결정

| ID | 결정 | 선택지 | 권장안 | 이유 |
|---|---|---|---|---|
| D-1 | 웹 등록에 비밀번호를 요구하는 규칙 | (a) push와 같은 규칙: "읽기·쓰기"와 "push만"이면 비밀번호, "끄기"면 없이 / (b) 설정과 상관없이 항상 비밀번호 | **(a)** | 미러 등록은 폰의 저장 공간과 네트워크를 쓰는 쓰기 동작이라 push와 같은 무게다. "push만"에서 익명 사용자가 등록할 수 없게 된다. "끄기"는 사용자가 이미 push까지 열기로 고른 상태다. 이 경우 R2-06의 원칙(사용자 설정을 그대로 따름)과 맞춘다. (b)를 고르면 "끄기" 상태에서도 이 경로만 비밀번호 창이 떠서 동작이 일관되지 않다. |
| D-2 | 외부 공개(ngrok) 경로에서도 웹 등록을 허용할지 | (a) 허용, D-1 규칙 그대로 / (b) ngrok 경로에서는 항상 거부하고 웹에 이유 표시 / (c) 설정 스위치로 선택 | **(b)** | ngrok 주소는 인터넷에 열려 있다. 등록을 허용하면 바깥의 누구나(또는 비밀번호를 알아낸 사람이) 폰이 임의 주소로 나가 수 GB를 받게 만들 수 있다. 등록은 같은 네트워크와 Tailscale에서도 충분하다. 조용히 무시하지 않고 "외부 공개 주소에서는 미러를 추가할 수 없어요"를 보여 주므로 R2-06의 "조용한 무시를 없앤다" 원칙과도 충돌하지 않는다. (c)는 설정 항목만 늘린다. |
| D-3 | 비공개 레포 토큰을 웹에서 입력받을지, 저장된 토큰을 쓸지 | (a) 입력 안 받음, 저장된 토큰도 안 씀(공개 레포만) / (b) 입력 안 받음, 비밀번호로 인증된 요청이면 앱에 저장된 그 호스트 토큰을 앱과 같은 규칙으로 씀 / (c) 웹에서 토큰 입력도 받음 | **(b)** | 웹으로 토큰을 보내면 LAN 평문 HTTP 구간에 토큰이 지나간다. 토큰 관리 화면도 두 곳이 된다. 그래서 입력은 받지 않는다. 다만 앱에 이미 토큰을 넣어 둔 사용자가 웹에서 비공개 레포를 못 넣는 것은 불편하다. 그러니 비밀번호로 확인된 요청에서만 저장된 토큰을 쓴다. 익명 요청("끄기")에서는 쓰지 않는다. 그래야 익명 사용자가 폰의 토큰으로 비공개 레포를 끌어와 읽는 일을 막는다. 토큰이 없거나 거부되면 "앱에서 토큰을 등록하세요"로 안내한다. |
| D-4 | 계정·조직 일괄 미러, 여러 줄 등록까지 할지 | (a) 한 개씩만 / (b) 여러 줄 URL까지 / (c) 계정·조직 일괄까지 | **(a)** | 요청은 "링크를 붙여 넣어 등록"이다. (b)는 웹에 일괄 진행 화면이 필요하고, (c)는 카탈로그 API·레이트리밋·선택 목록까지 옮겨야 한다. 한 개 등록이 자리를 잡은 뒤 다시 본다. |
| D-5 | 웹에서 받는 원격 주소를 https로만 제한할지 | (a) https만 / (b) 앱처럼 http도 허용(경고 표시) | **(a)** | 웹 등록은 폰이 사용자가 준 주소로 직접 나가는 요청이다. http를 막으면 같은 망 안의 내부 서비스로 요청을 보내는 데 쓰일 여지가 크게 준다. GitHub·GitLab은 모두 https다. http 원격이 필요하면 앱에서 등록한다. |
| D-6 | 웹에서 등록됐을 때 폰에 알릴지 | (a) 따로 알리지 않음(목록 반영, 접속 기록) / (b) 알림 한 번 | **(a)** | 첫 받기 실패나 원본 문제는 기존 알림(F-12)이 그대로 알린다. 등록 자체를 알리는 알림은 소음이 된다. 누가 등록했는지는 접속 기록에 남는다. |

### 5.2 위험
| # | 위험 | 정도 | 대응 |
|---|---|---|---|
| 1 | **앱이 백그라운드일 때 첫 받기가 늦게 시작될 수 있다.** 웹에서 등록하는 순간 사용자는 대개 PC 앞에 있고, 폰의 앱 화면은 닫혀 있다. spec에는 백그라운드에서 포그라운드 작업을 못 얻으면 첫 받기를 미루는 경로(`waitingForForeground`, GIT-08)가 있다. 서버 포그라운드 서비스가 돌고 있으니 시작될 가능성이 높지만, 기기에서 확인하지 않았다. | 높음 | 구현 전에 코어가 실기기에서 먼저 확인한다. 미뤄지면 웹에 "폰에서 앱을 열면 받기를 시작해요"를 보여 준다. 이 기능의 체감 품질을 가장 크게 좌우한다. |
| 2 | CSRF 방어 누락 | 높음 | 세 겹 방어(2장)와 QA 시험 페이지. 하나라도 빠지면 출시하지 않는다. |
| 3 | 폰이 원격 주소로 나가는 요청의 오남용(내부망 탐색, 대용량 받기) | 중간 | D-2(ngrok 거부), D-5(https만), 인증(D-1), 저장 공간 하한, probe 동시 상한 |
| 4 | "웹은 읽기 전용" 결정이 무너지면서 다른 쓰기 요구가 따라 들어옴 | 중간 | PRD에 "미러 추가 하나만 예외"로 명시하고, 3.7을 범위 밖 표에 옮긴다. |
| 5 | probe가 웹 요청을 오래 붙잡음 (원격이 느리면 최대 120초) | 낮음 | 웹 경로 전용 제한 시간과 동시 상한, 503 `BUSY` |
| 6 | 브라우저의 Basic 인증 프롬프트: "push만" 설정에서 읽기는 익명이라 브라우저에 자격 증명이 없다. 등록 버튼을 누르는 순간 401이 나며 프롬프트가 뜬다 | 낮음 | 웹이 등록 전에 `/api/v1/info`로 상태를 확인하고 "등록하려면 비밀번호가 필요해요"를 먼저 안내한다. 401 응답으로 브라우저 프롬프트를 띄우는 방식은 그대로 둔다. |
