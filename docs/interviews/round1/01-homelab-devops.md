# 인터뷰 01 — 홈랩 운영하는 DevOps/인프라 엔지니어

- 경력: 12년 차 DevOps/인프라 엔지니어
- 업무 환경: 회사에서 GitLab(Self-managed)과 GitHub Enterprise Server 운영
- 개인 환경: Synology NAS(DS920+) Docker 위에 Forgejo, 라즈베리파이 4(8GB)에 예전 Gitea 인스턴스, Tailscale로 묶어서 사용
- 사용 기기: 갤럭시 S23 (메인), 예전에 쓰던 픽셀 6a는 서랍에 있음

---

## 1. 지금 레포 백업/미러링을 어떻게 하고 있나요? (작업 흐름)

순서대로 말하면 이렇습니다.

1. **미러 대상 고르기**
   GitHub 스타 목록이나 회사 업무에서 의존하는 오픈소스(예: 특정 Helm 차트, Terraform 프로바이더, 작은 Go 라이브러리)를 보다가 "이거 언젠가 사라지면 곤란하겠다" 싶은 걸 고릅니다. 2022년쯤 쓰던 라이브러리 하나가 저자 계정 삭제로 통째로 날아간 적이 있어서 그 뒤로 습관이 됐어요. 기준은 대충 "스타 적고, 메인테이너 한 명이고, 내가 실제로 빌드에 쓰는 것".

2. **Forgejo에 Pull Mirror 생성**
   NAS의 Forgejo 웹 UI에서 "New Migration → GitHub"로 들어가서 URL 붙여넣고 "This repository will be a mirror"를 체크합니다. 개인 private 레포는 GitHub PAT(fine-grained, read-only)를 넣고요. 이슈/PR/위키까지 같이 가져오는 옵션은 처음엔 다 켰는데 지금은 코드와 위키만 받습니다. 이슈 마이그레이션은 GitHub API 레이트리밋 걸리고 느려서요.

3. **동기화 주기 설정**
   기본 8시간인데 대부분 24h로 늘려 둡니다. 레포가 200개 넘어가니까 NAS가 새벽에 한꺼번에 fetch하면서 디스크 I/O가 튀어서, 일부는 수동으로 주기를 엇갈리게 바꿨어요.

4. **내 개인 레포는 반대 방향(Push Mirror)**
   개인 프로젝트는 Forgejo가 원본이고, GitHub로 push mirror를 걸어 둡니다. 원본을 내 손에 두고 GitHub는 "공개용 사본" 취급.

5. **NAS 자체 백업**
   Forgejo 데이터 디렉터리(`/data/git/repositories`)와 SQLite DB를 Hyper Backup으로 외장 HDD와 Backblaze B2에 매일 백업합니다. 별도로 `forgejo dump`를 주 1회 cron으로 돌리고요.

6. **외부에서 접근**
   Tailscale로 NAS에 붙어서 `git clone ssh://git@nas.tailnet-xxxx.ts.net:2222/...` 식으로 씁니다. 공개 노출은 안 합니다. 리버스 프록시+도메인도 해봤는데 관리 포인트만 늘어서 접었어요.

7. **확인**
   사실 이게 제일 허술한데, 미러가 실패해도 한참 모르고 지냅니다. 가끔 Forgejo 관리자 페이지의 "Cron tasks"나 레포별 "Last updated"를 눈으로 훑는 정도예요.

회사 쪽은 GitLab의 Pull mirroring(Premium 기능)으로 외부 의존 레포 몇 개를 내부로 끌어오고, GitHub Enterprise는 `git clone --mirror` + cron 스크립트로 S3에 번들을 떨굽니다. 이건 업무라 결이 좀 다르니 참고 정도로만요.

## 2. 단계별 불편한 점과 있었으면 하는 기능

| 단계 | 불편했던 점 | 있었으면 하는 것 |
|---|---|---|
| 대상 고르기 | GitHub 스타 목록과 미러 목록이 따로 놀아서 "이거 미러 걸었던가?"를 매번 확인함 | 스타/특정 org를 일괄 import, 이미 미러된 건 표시 |
| 미러 생성 | 레포 하나씩 웹 폼 클릭. 수십 개면 API 스크립트 짜야 함 | URL 여러 줄 붙여넣기로 일괄 등록 |
| 인증 | PAT 만료되면 private 미러가 조용히 실패. fine-grained 토큰은 기본 만료가 있어서 더 자주 터짐 | 토큰 만료 임박/인증 실패를 바로 알림 |
| 동기화 주기 | 전부 같은 시간에 몰려서 부하 스파이크 | 자동으로 시간 분산(jitter), 원격에 변화 없으면 `ls-remote`로 가볍게 끝내기 |
| 원본 force-push/삭제 | 원본이 force-push 하면 미러도 그대로 덮어써짐. 아카이브 목적이면 이게 최악 | **원본이 히스토리를 지우거나 레포가 사라져도 내 쪽은 보존**. 덮어쓰기 전 이전 ref를 `refs/archive/...`로 남기는 옵션 |
| 백업 | Forgejo 백업 + NAS 백업 이중이라 복원 절차가 헷갈림. 실제로 복원 연습은 한 번밖에 안 해봄 | 레포 단위 `git bundle` 내보내기, 복원 테스트가 쉬운 구조 |
| 외부 접근 | Tailscale 없는 기기(회사 PC 등)에서는 못 씀. SSH 포트 따로 열어야 하는 것도 번거로움 | HTTPS(smart HTTP) 하나로 clone/pull 되면 충분 |
| 모니터링 | 실패를 모름. 로그 찾으려면 컨테이너 들어가야 함 | 실패한 미러만 모아 보는 화면, 마지막 성공 시각 |
| 저장공간 | 대형 레포(예: 커널, Chromium 계열)를 실수로 걸면 디스크가 순식간에 참 | 등록 전 예상 크기 표시, shallow/특정 브랜치만 옵션, LFS 제외 옵션 |

## 3. 이런 앱이 있다면 언제 쓰겠나요? 쓰지 않을 이유는?

### 쓸 것 같은 상황
- **출장/여행 중 노트북만 들고 갔을 때.** 집 NAS가 정전이나 공유기 문제로 죽으면 Tailscale로도 못 붙습니다. 실제로 작년 추석에 집 공유기가 재부팅 루프 돌아서 4일간 홈랩 접근을 못 했어요. 폰에 핵심 레포 20~30개라도 있으면 "두 번째 사본"으로 의미가 있습니다.
- **비행기/오프라인 환경에서 노트북과 폰을 핫스팟으로 묶어서** 레퍼런스 코드 clone. 폰이 항상 들고 다니는 기기라는 게 장점이에요.
- **"사라질 것 같은" 레포를 그 자리에서 바로 저장.** 지하철에서 HN이나 GeekNews 보다가 "이거 DMCA 맞을 것 같은데" 싶은 레포를 URL 공유 → 앱으로 바로 미러. 이 흐름은 NAS로는 귀찮아서 안 하게 되거든요. **안드로이드 공유 시트(Share intent) 지원**이 있으면 이 시나리오 하나만으로도 설치할 이유가 됩니다.
- 남는 구형 폰(픽셀 6a)을 충전기에 꽂아 두고 **초소형 상시 미러 서버**로 쓰는 것. 라즈베리파이보다 배터리(=UPS) 내장이라 오히려 낫다고 생각해요.

### 쓰지 않을 이유
- **신뢰성.** 안드로이드는 백그라운드 작업을 수시로 죽입니다(Doze, 제조사별 배터리 최적화 — 특히 삼성). "업데이트를 따라간다"고 했는데 실제로 며칠 동안 동기화가 안 됐는데 모르면 의미가 없어요. 이게 제일 큰 불안 요소입니다.
- **보안.** 폰을 ngrok으로 인터넷에 노출한다? 업무 레포는 절대 안 올립니다. 회사 보안 정책상도 안 되고요. 개인 레포도 ngrok 주소가 공개 URL인데 인증이 허술하면 곤란합니다. 기본값은 반드시 "외부 노출 꺼짐"이어야 해요.
- **폰 분실/파손.** 폰이 유일한 사본이면 백업이 아니라 리스크죠. 폰에서 다시 다른 곳(NAS, 클라우드)으로 내보낼 수 있어야 진짜 아카이브입니다.
- **저장공간과 배터리.** 128GB 폰에 레포 수십 GB는 부담. 모바일 데이터로 큰 fetch가 돌면 요금 문제도.
- **push 대상으로서는 글쎄.** PC에서 폰으로 push하는 건 솔직히 잘 안 쓸 것 같습니다. 원격으로 쓸 거면 NAS나 GitHub가 낫고, 폰은 "읽기 위주 사본"에 가깝게 생각해요. 있으면 좋지만 핵심은 아님.

## 4. 비교하거나 참고할 제품

| 제품 | 좋은 점 | 아쉬운 점 |
|---|---|---|
| **Forgejo / Gitea** (현재 메인) | Pull/Push mirror가 내장, 웹 UI 익숙함, 가볍다 | 미러 실패 알림 약함, 일괄 등록 불편, force-push 보존 안 됨, 결국 서버가 있어야 함 |
| **GitLab Pull mirroring** (회사) | 안정적, 실패 시 UI에 표시, 보호 브랜치 diverge 감지 | Premium 이상, 무겁다, 개인용으론 과함 |
| **Soft Serve** (Charm) | 단일 바이너리, SSH 기반 TUI가 예쁨, 설정이 간단 | 미러링 기능은 기초적, 웹 UI 없음 |
| **ghorg** | GitHub org/유저 레포 일괄 clone에 최고. 백업 스크립트 대용 | 그냥 clone 도구라 서빙/브라우징 없음 |
| **gickup** | GitHub/GitLab/Gitea 등에서 여러 곳으로 백업하는 설정이 깔끔 | 별도 서버/cron 필요, 브라우징 없음 |
| **Software Heritage** | "사라진 코드" 아카이빙 철학 그대로. 공개 레포 보존용으로 신뢰 | 내 통제 밖, private 불가, 원할 때 바로 clone하기 불편 |
| **Termux + git / gitea 바이너리** | 실제로 폰에서 Gitea를 띄워본 적 있음(arm64 바이너리). 동작은 함 | 백그라운드에서 금방 죽고, wakelock·자동시작·업데이트 다 수동. 이 앱이 해결해야 할 정확히 그 문제 |
| **Working Copy (iOS), MGit (Android)** | 모바일 git 클라이언트로서 UX 참고할 만함 | 서버 역할은 없음. MGit은 업데이트가 거의 멈춤 |
| **Syncthing** | 기기 간 동기화 신뢰성, 충돌 처리, 백그라운드 동작 노하우 | git 인식 없음. `.git` 폴더 싱크하면 망가짐(경험담) |

특히 **Termux로 Gitea 띄웠다가 포기한 경험**이 이 앱이 해결할 지점을 잘 보여준다고 생각합니다. 서버 기능 자체보다 "안드로이드에서 안 죽고 계속 도는 것"이 진짜 난제예요.

## 5. 꼭 있어야 하는 것 3가지 / 없어도 되는 것

### 꼭 있어야 하는 것
1. **신뢰할 수 있는 동기화와 상태 가시성.** 레포별 마지막 성공 시각, 실패 사유, 실패 시 알림. 포그라운드 서비스든 WorkManager든 "제 시간에 돌았다"는 걸 증명해 줘야 합니다. 와이파이+충전 중일 때만 동기화 같은 조건 설정도 이 범주.
2. **아카이브 보존 정책.** 원본이 force-push하거나 브랜치/태그를 지우거나 레포가 404가 되어도 내 쪽 데이터는 남아야 합니다. 덮어쓰기 전 기존 ref를 보관하고, "원본 사라짐" 상태를 표시해 주면 완벽. 이게 Forgejo 미러와 차별화될 수 있는 지점이에요.
3. **표준 git 프로토콜(smart HTTP)로 clone/fetch + 기본 인증.** PC에서 그냥 `git clone http://192.168.x.x:port/foo.git`이 되어야 합니다. 커스텀 클라이언트 필요하면 안 씀. 그리고 외부 노출(ngrok)은 기본 OFF, 켤 때는 토큰/비밀번호 필수.

(번외로 하나 더 꼽으라면: 폰에서 다른 곳으로 **내보내기**(`git bundle` 또는 다른 원격으로 push mirror). 폰이 유일한 사본이 되면 안 되니까요.)

### 없어도 되는 것
- **이슈/PR/위키 마이그레이션.** 코드만 있으면 됩니다. 위키는 별도 git 레포라 그냥 레포로 받으면 되고요.
- **웹에서 코드 편집, 웹 IDE.** 브라우징(파일 트리, README 렌더링, 커밋 로그) 정도면 충분.
- **사용자/조직/권한 관리.** 1인용이면 계정 하나 + 토큰이면 됩니다.
- **CI/Actions, 웹훅.** 폰에서 돌릴 이유 없음.
- **폰에서 직접 커밋하는 에디터 기능.** 다른 앱 영역입니다.
- **ngrok 내장 연동은 우선순위 낮음.** 저는 Tailscale만 쓸 거라, ngrok은 "지원하면 좋다" 정도. 오히려 Tailscale Funnel이나 Cloudflare Tunnel 같은 선택지를 열어두는 게 나을 수도.

## 6. 그 외에 하고 싶은 말

- **"서버"보다 "아카이브"를 앞에 두세요.** 홈랩 하는 사람들은 이미 서버가 있습니다. 그런데 "주머니 속 두 번째 사본", "공유 버튼 한 번으로 보존"은 아무도 잘 안 해줘요. 포지셔닝을 거기에 두면 저 같은 사람도 씁니다.
- **저장공간 투명성.** 레포별 용량, 전체 사용량, git gc 실행 버튼(또는 자동 gc). 미러 오래 돌리면 pack 파일이 쌓입니다.
- **원본 서버에 예의 바르게.** 수백 개 레포를 한꺼번에 fetch하면 GitHub 쪽 레이트리밋/차단 걸릴 수 있어요. 동시성 제한과 backoff는 기본으로.
- **LFS와 서브모듈 처리 방침을 명확히.** 지원 안 하면 안 한다고 표시만 해줘도 됩니다. 조용히 빠지면 나중에 복원할 때 낭패.
- **설정/레포 목록 내보내기(가져오기).** 폰 바꿀 때 목록을 YAML이나 JSON으로 옮길 수 있으면 좋겠어요. gickup 설정 파일처럼.
- **삼성 배터리 최적화 안내 화면.** "이 앱을 절전 예외로 등록하세요" 가이드가 앱 안에 있으면 지원 문의가 확 줄 겁니다. dontkillmyapp.com 참고하세요.
- 마지막으로, 첫 버전은 **pull mirror + HTTP clone + 상태 화면**만 잘 돼도 저는 서랍 속 픽셀에 깔아서 써볼 의향이 있습니다. 나머지는 그다음이에요.
