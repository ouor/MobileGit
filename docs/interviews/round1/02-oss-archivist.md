# 인터뷰 02: OSS 아카이브 담당 연구자

- **응답자**: 대학 소프트웨어공학 연구실 박사후연구원
- **배경**: 실증 연구(MSR, Mining Software Repositories)용으로 오픈소스 레포 수백 개를 수집·보관. 원본 삭제나 비공개 전환으로 연구 자료를 잃은 적이 여러 번 있음. 개인적으로 좋아하는 프로젝트도 따로 백업함.
- **라운드**: 1

---

## 1. 지금은 레포를 어떻게 수집·백업·미러링하나요? (작업 흐름)

연구용과 개인용 흐름이 다릅니다. 연구용이 훨씬 체계적이에요.

### 연구용 (논문 데이터셋)

1. **후보 선정**: GitHub Search API나 GHArchive, 가끔 SEART GitHub Search 같은 데이터셋 검색 도구로 조건(언어, 스타 수, 커밋 수, 최근 활동)을 걸어 후보 목록을 CSV로 뽑습니다. 보통 300~800개 정도예요.
2. **일괄 clone**: 파이썬 스크립트로 CSV를 돌면서 `git clone --mirror`를 합니다. 연구실 서버(우분투, 20TB짜리 RAID 볼륨)에 `owner__repo.git` 형식으로 저장해요. rate limit 때문에 토큰을 몇 개 돌려 쓰고, 실패한 건 로그로 남겨서 다시 돌립니다.
3. **스냅샷 고정**: 논문에 쓸 시점이 정해지면 레포마다 HEAD 커밋 SHA를 기록한 manifest(CSV + JSON)를 만듭니다. 이게 재현성의 핵심이에요. "2025년 3월 14일 기준 이 SHA"라고 고정해야 리뷰어가 똑같이 돌려볼 수 있으니까요.
4. **메타데이터 따로 수집**: 이슈, PR, 릴리스, 스타 수 같은 건 git에 안 들어 있어서 GitHub API로 JSON 덤프를 따로 받습니다. 이게 제일 귀찮고 제일 자주 깨져요.
5. **주기적 업데이트**: 장기 추적 연구면 cron으로 주 1회 `git remote update --prune`를 돌립니다. 그런데 `--prune` 때문에 원본에서 force-push로 지워진 브랜치가 우리 쪽에서도 사라진 적이 있어서, 지금은 업데이트 전에 refs를 따로 백업해 둡니다.
6. **장기 보관**: 논문 게재가 확정되면 manifest와 tar로 묶은 bare 레포를 Zenodo에 올리고 DOI를 받습니다. 용량이 크면 Software Heritage SWHID만 적고 끝내기도 해요.

### 개인용

- 좋아하는 프로젝트(주로 작은 CLI 도구, 에디터 플러그인, 사라질 것 같은 1인 개발 프로젝트)는 집에 있는 시놀로지 NAS의 Gitea에 "Pull mirror"로 걸어 둡니다. 지금 120개쯤 돼요.
- 급할 때는 폰으로 GitHub 링크를 보다가 "이거 나중에 없어질 것 같다" 싶으면 Pocket에 저장하거나 저한테 카톡으로 링크를 보내 두고, 나중에 PC 앞에 앉아서 Gitea에 등록합니다. 솔직히 그 사이에 잊어버리는 게 절반이에요.

## 2. 단계별 불편한 점과 있었으면 하는 기능

| 단계 | 불편했던 점 | 있었으면 하는 기능 |
|---|---|---|
| 발견 → 저장 | 폰에서 발견한 레포를 바로 백업할 방법이 없음. 링크 메모 후 잊어버림 | 공유 메뉴(Share intent)에서 "이 레포 미러링" 한 번에 끝나는 것 |
| 일괄 clone | 스크립트가 중간에 죽으면 어디까지 했는지 다시 확인해야 함. 대용량 레포(수 GB)는 타임아웃 | 목록(CSV/텍스트) 일괄 등록, 실패 항목만 재시도, 진행 상태 표시 |
| 업데이트 추적 | force-push나 브랜치 삭제가 미러에 그대로 반영돼서 과거 상태가 사라짐 | **덮어쓰기 전 refs 보존**(예: `refs/archive/<날짜>/...`), 업데이트 이력 로그 |
| 원본 사라짐 감지 | 원본이 404가 된 걸 몇 달 뒤에야 앎. Gitea는 그냥 조용히 sync 실패만 남김 | 원본이 삭제/비공개/이름 변경/아카이브 됐을 때 알림. "이 미러는 이제 유일한 사본입니다" 표시 |
| 스냅샷 고정 | SHA manifest를 손으로 만듦 | 특정 시점의 전체 레포 SHA 목록을 CSV/JSON으로 내보내기 |
| 메타데이터 | 이슈/릴리스는 git에 없어서 원본 사라지면 같이 날아감 | (있으면 좋음) 릴리스 첨부파일, README 렌더 정도라도 같이 보관 |
| 무결성 | 디스크 오류로 pack 파일이 깨진 걸 늦게 발견한 적 있음 | 주기적 `git fsck`와 결과 표시 |
| 장기 보관 | NAS도 결국 한 곳. 이중화가 귀찮음 | 다른 원격(NAS, 연구실 서버)으로 다시 push하는 2차 미러 |

제일 아팠던 경험 하나를 말하자면, 2023년에 리팩터링 탐지 연구를 하면서 쓰던 레포 중 11개가 1년 사이에 사라졌어요. 7개는 저희가 `--mirror`로 받아 둬서 살았는데, 4개는 초기에 `--depth 1`로 받아 둔 거라 히스토리가 없어서 재현 실험을 못 했습니다. 리뷰어한테 "데이터셋 일부를 재현할 수 없다"고 써야 했죠. 그 뒤로 **무조건 full mirror**가 원칙이에요.

## 3. 이런 앱이 있다면 언제 쓰고, 언제 안 쓸까요?

### 쓸 것 같은 상황

- **이동 중 발견한 레포 즉시 보존**: 학회 가는 길, 트위터/해커뉴스에서 "이 프로젝트 곧 닫는다"는 글을 봤을 때. 이게 제일 큰 이유예요. 공유 버튼 한 번으로 끝나면 바로 씁니다.
- **개인 백업 보조 사본**: NAS 말고 물리적으로 다른 곳에 있는 사본 하나 더. 폰은 늘 들고 다니니까 "집에 불나도 남는 사본"이 되는 셈이죠.
- **학회·출장지에서 데모**: 와이파이 불안정한 곳에서 노트북으로 폰에 있는 레포를 clone해서 보여줄 수 있으면 좋겠어요. 학회장 와이파이는 GitHub도 느릴 때가 많거든요.
- **작은 레포를 브라우저로 훑어보기**: 폰에서 바로 코드를 볼 수 있으면 지하철에서 리뷰 대상 레포를 미리 볼 수 있음.

### 안 쓸 이유

- **용량**: 연구 데이터셋은 수백 GB예요. 폰에는 절대 못 넣습니다. 연구용 메인 저장소로는 안 씁니다. 개인용 100~200개, 합쳐서 수십 GB 이내가 현실적인 범위예요.
- **신뢰성**: 폰은 잃어버리고, 떨어뜨리고, 기변합니다. 폰이 "유일한 사본"이 되는 건 불안해요. 폰에 있는 걸 다른 곳으로 내보내는 경로가 없으면 오히려 위험합니다.
- **백그라운드 제약**: 안드로이드가 백그라운드 작업을 막 죽이잖아요. 주기적 동기화가 실제로 돌았는지 확신이 안 서면 아카이브로 못 믿어요.
- **외부 노출**: ngrok으로 폰을 인터넷에 여는 건 연구실 보안 정책상 좀 꺼려집니다. Tailscale은 괜찮아요. 이미 쓰고 있고요.
- **배터리/발열**: 수 GB 레포 clone 하다가 폰이 뜨거워지면 그냥 안 쓸 것 같아요. 충전 중 + 와이파이일 때만 큰 작업 하는 옵션이 필요합니다.

## 4. 비교·참고할 제품

| 제품 | 좋은 점 | 아쉬운 점 |
|---|---|---|
| **Gitea / Forgejo (NAS에 설치)** | Pull mirror 설정이 쉽고 웹 UI 좋음. 지금 주력 | 원본 삭제 감지 없음, sync 실패가 조용함. force-push 시 과거 refs 보존 안 됨. NAS 관리 부담 |
| **Software Heritage** | 사실상 표준 아카이브. SWHID로 논문 인용 가능. "Save code now" 기능 | 원하는 시점에 즉시 받아 오는 게 보장 안 됨(큐 대기). 대용량 일괄 다운로드가 번거로움(vault 요청 후 대기) |
| **Zenodo + GitHub 연동** | 릴리스 단위로 DOI 발급. 논문 재현성 패키지로 좋음 | 릴리스 안 하는 레포는 안 됨. 히스토리 전체가 아니라 tarball |
| **ghorg, `gh repo clone` 스크립트** | 조직 단위 일괄 clone 편함 | 업데이트 추적·상태 관리는 직접 해야 함 |
| **GitHub Archive Program / Arctic Vault** | 상징적 의미 | 개인이 원하는 걸 넣을 수 없고 꺼내기도 어려움 |
| **archive.org (Wayback)** | 레포 페이지 자체는 남음 | git 히스토리는 없음. clone 불가 |
| **Termux + git** | 폰에서 이미 이걸로 몇 번 해봄. 자유도 높음 | 서버로 열려면 sshd 설정, 포트, 백그라운드 유지 다 손으로 해야 함. 비개발자 수준으로는 못 씀. 이 앱이 사실상 "Termux로 하던 걸 버튼으로" 만드는 거라고 봐요 |
| **GitJournal, MGit 같은 안드로이드 git 클라이언트** | 폰에서 clone/브라우징 가능 | 서버 역할(PC에서 clone 받기)은 안 됨. 미러 자동 업데이트도 없음 |

## 5. 꼭 있어야 하는 것 3가지 / 없어도 되는 것

### 꼭 있어야 하는 것

1. **완전한 미러(`--mirror` 수준)와 히스토리 보존**: 모든 브랜치·태그 포함. shallow clone은 아카이브가 아닙니다. 그리고 원본에서 force-push나 브랜치 삭제가 일어나도 **기존 refs를 지우지 않는 옵션**(기본값이면 더 좋음). 아카이브 목적이면 "원본을 그대로 따라가는 것"보다 "잃지 않는 것"이 우선이에요.
2. **원본 상태 감시와 알림**: 마지막 동기화 시각, 성공/실패, 원본이 404/비공개/이름 변경됐는지를 레포 목록에서 한눈에. 원본이 사라졌을 때 푸시 알림. 이게 있으면 이 앱만의 확실한 가치가 생깁니다. Gitea도 못 해 주는 부분이라.
3. **폰 밖으로 쉽게 꺼내기**: PC에서 `git clone`이 되는 건 기본이고, 추가로 레포 목록과 SHA manifest 내보내기(JSON/CSV), 가능하면 다른 원격(NAS 등)으로 2차 push. 폰이 유일한 사본이 되면 안 되니까요.

(번외로 하나 더 꼽자면, 공유 메뉴에서 URL 받아서 바로 등록하는 것. 진입 장벽을 없애는 기능이라 사실상 필수에 가까워요.)

### 없어도 되는 것

- **폰에서 직접 코드 편집, 커밋 작성**: 폰으로 코드 안 짭니다.
- **이슈 트래커, PR, 코드 리뷰 같은 협업 기능**: Gitea 흉내 낼 필요 없어요.
- **화려한 웹 UI**: 파일 트리, README 렌더, 커밋 로그, 파일 내용 보기 정도면 충분. 구문 강조는 있으면 좋고 blame이나 diff 시각화는 없어도 됩니다.
- **ngrok 연동**: 저는 Tailscale로 충분하고, 공개 URL은 보안상 오히려 부담이에요. 넣더라도 기본은 꺼 두고 인증 필수로.
- **push 받기(쓰기)**: 아카이브 용도로는 읽기 전용이면 충분합니다. 오히려 실수로 미러에 push 하는 걸 막아 주는 게 나아요. 개인 프로젝트 원격으로 쓰는 분들은 필요하겠지만 저한테는 우선순위 낮음.

## 6. 그 외에 하고 싶은 말

- **"미러"와 "아카이브"는 다릅니다.** 미러는 원본을 따라가고, 아카이브는 잃지 않는 게 목적이에요. 원본이 브랜치를 지우면 미러는 지우고 아카이브는 남겨야 합니다. 앱이 어느 쪽인지 명확히 하거나, 레포별로 모드를 고를 수 있게 해 주세요. 저는 무조건 아카이브 모드요.
- **용량 표시가 중요합니다.** 레포별 크기, 전체 사용량, 남은 공간. 등록 전에 "이 레포는 대략 2.3GB입니다" 같은 예상치를 보여 주면 좋겠어요(GitHub API의 `size` 필드로 대충 알 수 있음).
- **LFS와 서브모듈**: 연구용 레포 중에 LFS로 데이터를 넣어 둔 게 꽤 있는데, LFS 객체 없이 받으면 반쪽짜리예요. 최소한 "이 레포는 LFS를 쓰는데 LFS 객체는 안 받았음"이라고 표시라도 해 주세요. 서브모듈도 마찬가지로, 서브모듈 원본이 사라지면 같이 의미가 없어집니다.
- **백그라운드 동기화를 정직하게 보여 주세요.** "마지막 성공 동기화: 3일 전" 같은 정보를 숨기지 말고요. 안드로이드가 작업을 죽였으면 죽였다고 알려 주는 게, 조용히 실패하는 것보다 백배 낫습니다.
- **라이선스 메모**: 아카이브한 레포를 나중에 재배포할 때 라이선스 확인이 필요한데, 등록 시점의 LICENSE 파일 종류를 기록해 두면 연구자 입장에선 꽤 쓸모 있어요. 필수는 아닙니다.
- 마지막으로, 이 앱의 진짜 경쟁 상대는 "나중에 PC에서 해야지" 하고 잊어버리는 저 자신이에요. 폰에서 발견한 순간 3초 안에 보존이 끝나면, 용량이나 다른 단점이 있어도 쓸 겁니다.
