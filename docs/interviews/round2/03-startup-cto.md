# 인터뷰 03 — 스타트업 CTO (개발자 6명, 경력 14년)

- 회사 코드: GitHub Organization (Team 플랜), 레포 약 40개 (실제로 살아 있는 건 12~15개)
- 배경: 시리즈 A 실사, ISMS 준비 과정에서 "GitHub가 막히거나 계정이 정지되면 코드는 어떻게 되나요?"를 반복해서 질문받음
- 성향: 돈과 관리 시간 모두 아까워함. "한 번 설정하면 잊어도 되는 것"을 원함

---

## 1. 지금 회사 코드 백업·재해 대비를 어떻게 하고 있나

솔직히 말하면 "감사에 대답할 수 있을 만큼"만 하고 있습니다. 순서대로 보면 이렇습니다.

1. **원본은 GitHub Org 하나.** 모든 레포가 여기 있고, 개발자 6명은 각자 노트북에 clone해 둡니다. 사실 제일 현실적인 백업은 "6명 노트북에 흩어진 사본"인데, 이건 브랜치가 다 다르고 아무도 보장해 주지 않아서 감사 때 이것만 내밀 수는 없습니다.
2. **야간 미러 스크립트.** 사무실 Synology NAS에 쉘 스크립트 하나를 cron으로 돌립니다. GitHub API로 Org 레포 목록을 받아서 `git clone --mirror` / `git remote update --prune`를 돌립니다. 인증은 처음엔 제 개인 PAT였다가, 실사 때 "퇴사하면 어떻게 되냐"는 지적을 받고 fine-grained PAT(읽기 전용, Org 소유)로 바꿨습니다. 2년 전에 제가 직접 짠 거라 지금은 저만 고칠 줄 압니다.
3. **오프사이트 사본.** NAS의 미러 폴더를 주 1회 `git bundle`로 묶어서 S3(버전 관리 켠 버킷, Glacier 수명 주기)에 올립니다. 비용은 한 달에 몇천 원 수준이라 불만은 없습니다.
4. **이슈·PR·위키 같은 메타데이터.** 사실상 안 하고 있습니다. 분기에 한 번 정도 GitHub의 Org 마이그레이션 export를 손으로 떠서 같은 S3에 넣는 게 전부입니다. 깜빡하는 분기가 더 많습니다.
5. **복구 훈련.** 1년에 한 번, 인증 심사 직전에 합니다. S3에서 bundle 하나 내려받아서 `git clone`해 보고, 빌드 돌려 보고, 그 과정을 캡처해서 "복구 테스트 결과서"로 냅니다. 반나절 걸립니다.
6. **감사 대응.** 심사원이 "백업 주기, 보관 위치, 접근 권한, 복구 테스트 기록"을 물으면 위 내용을 워드 문서로 정리해서 냅니다. 증적은 cron 로그 캡처와 S3 콘솔 스크린샷입니다.

## 2. 단계별로 불편했던 점과 있었으면 하는 기능

| 단계 | 겪은 일 | 있었으면 하는 것 |
|---|---|---|
| 미러 스크립트 | **PAT가 만료돼서 3주 동안 백업이 조용히 실패**한 적이 있습니다. cron은 돌았고, 로그에 401만 쌓였고, 아무도 몰랐습니다. 심사 직전에 발견해서 식은땀 났습니다. | 실패하면 바로 알려 주는 것. 토큰 만료 D-14 경고. "마지막 성공 시각"이 한눈에 보이는 화면 |
| 레포 목록 | 새 레포를 만들면 스크립트가 자동으로 잡긴 하는데, 반대로 **아카이브/삭제된 레포의 사본을 스크립트가 같이 지워 버리는** 버그가 한 번 있었습니다. 백업이 원본 삭제를 따라가면 백업이 아닙니다. | 원본이 사라져도 사본은 남고 "원본 삭제됨" 표시만 되는 것. 새 레포 자동 포함 |
| force-push | 누가 main에 force-push 했을 때 `--prune` 때문에 이전 커밋이 미러에서도 날아갔습니다. 다행히 다른 사람 로컬에 있었습니다. | 히스토리가 덮어써지면 이전 ref를 별도로 보존하고 알려 주는 것 |
| LFS | 디자인 에셋 레포가 LFS인데, `clone --mirror`는 LFS 객체를 안 가져옵니다. 1년 넘게 모르고 있었습니다. | LFS 포함 여부를 명시적으로 보여 주고 같이 받기 |
| 오프사이트 | NAS가 사무실에 있으니 사무실 화재·도난이면 NAS와 노트북이 같이 날아갑니다. 그래서 S3가 필요한데, 이 파이프라인이 또 하나의 관리 포인트입니다. | 백업 사본을 다른 곳(S3, NAS, 구글 드라이브)으로 정기적으로 내보내기 |
| 복구 훈련 | 반나절이 아깝습니다. 그리고 매번 "이 bundle이 진짜 온전한지"는 clone이 되는지로만 확인합니다. | 정기 무결성 검사(`git fsck`) 자동 실행 + 결과 기록 |
| 감사 증적 | 캡처 모으고 문서 만드는 게 제일 싫은 일입니다. | "최근 90일 동기화 성공/실패, 레포별 마지막 백업 시각, 무결성 검사 결과"를 PDF/CSV로 뽑아 주는 버튼 |

## 3. 스크린샷을 보고: 내 상황에 맞는가

전체 인상: **개인 개발자가 "내 레포를 폰에 들고 다니는" 앱으로는 잘 다듬어져 있습니다. 그런데 회사 코드의 "재해 대비 사본"으로 쓰기엔 운영·보안 쪽 화면이 아직 없습니다.** 제가 사려는 건 "레포를 둘러보는 앱"이 아니라 "안 보고 있어도 계속 잘 받고 있다는 확신"이라서요.

### 바로 쓸 수 있을 것 같은 부분

- **05-bulk-mirror.png (계정·조직 일괄 미러)**: 제 1순위 기능입니다. Org 넣고 "포크 숨기기 / 보관된 레포 숨기기" 체크하고 전체 선택하면 끝나는 흐름이 좋습니다. 이미 등록된 건 "등록됨" 표시가 되는 것도 좋고, 선택 용량·남은 공간을 같이 보여 주는 것도 좋습니다. 다만 아래 "빠진 부분"의 자동 포함 문제가 있습니다.
- **03-add-mirror.png (미러 추가)**: "접근 가능 · 브랜치·태그 26개 받기 · PR 브랜치 34개 제외"를 등록 전에 미리 보여 주는 게 아주 좋습니다. 저는 PR ref를 빼는 게 맞다고 봅니다. 등록 전에 토큰이 맞는지 검증해 주는 것도 제 PAT 사고를 생각하면 반갑습니다.
- **15-web-repo-home.png 오른쪽 "보존된 기록 0개"**: 이게 이 앱의 진짜 차별점이라고 봅니다. force-push나 원본 삭제 때 남겨 둔 기록이 몇 개인지 보이는 것. 근데 0개라서 실제로 어떻게 보이는지는 못 봤습니다.
- **06-repo-detail-mirror.png "동기화 이력" 탭**: 감사 증적의 재료가 될 수 있습니다. 안을 못 봐서 실패 기록도 남는지 궁금합니다.
- **11-storage.png "전체 백업 (zip)"**: 폰 하나에 다 넣는 건 불안해서, 여기서 밖으로 빼는 길이 있다는 게 중요합니다. 다만 수동 버튼 하나뿐입니다.
- **16-web-file-view.png, 17-web-commit-log.png**: 복구 훈련 때 "백업에 이 커밋까지 들어 있다"를 브라우저로 바로 보여 줄 수 있어서 심사원 앞에서 쓸모가 있겠습니다. 다만 우선순위는 낮습니다.

### 빠져 있거나 헷갈리는 부분

1. **실패가 어디에도 안 보입니다.** 01-main.png 레포 목록은 "업데이트 1분 전"만 있고, 실패한 레포나 "3일째 업데이트 안 됨" 같은 경고가 없습니다. 메인 상단에 "미러 12개 중 12개 정상 / 마지막 전체 동기화 성공 몇 분 전" 같은 한 줄이 제일 먼저 있어야 합니다. 제 3주 사고가 여기서 그대로 재현될 수 있습니다.
2. **토큰 관리 화면이 안 보입니다.** 03-add-mirror.png의 "원본 접속 토큰" 드롭다운은 있는데, 토큰이 어디에 저장되는지, 만료일이 언제인지, 어떤 레포가 이 토큰을 쓰는지 보는 화면이 없습니다. GitHub App 설치 방식이면 더 좋겠습니다(사람에 묶이지 않으니까요).
3. **일괄 미러가 "한 번 고르기"인지 "Org를 계속 따라가기"인지 모르겠습니다.** 05-bulk-mirror.png에서 2개 등록하고 나면, 다음 달 새로 생긴 레포는 자동으로 들어오나요? 저한테는 "이 Org 전체를 계속 미러" 토글이 필요합니다.
4. **동기화 주기가 안 보입니다.** 몇 분마다/몇 시간마다 따라가는지, 어디서 바꾸는지 10-settings.png에 없습니다. 감사에서 "백업 주기"는 반드시 묻는 항목입니다.
5. **보안 화면이 감사 관점에선 걱정스럽습니다.** 10-settings.png의 "연결 경로별 보안" 설명은 정직해서 좋습니다. 그런데 "와이파이: 암호화되지 않아요. 비밀번호를 엿볼 수 있어요"와 "ngrok: 인터넷의 누구나 접속을 시도할 수 있어요"를 보는 순간 심사원은 그 둘을 끄라고 할 겁니다. **"Tailscale로만 접속 허용" 같은 옵션**이 있어야 회사에서 쓸 수 있습니다. 또 사용자 이름이 `git` 하나, 비밀번호 하나인데, 회사에서는 사람별 계정(최소한 사람별 토큰)과 읽기 전용 권한이 필요합니다. 누가 언제 clone했는지 접근 기록도요.
6. **폰 자체를 잃어버렸을 때가 빠져 있습니다.** 회사 소스 전체가 들어 있는 폰입니다. 저장 데이터 암호화 여부, 앱 잠금, 원격 삭제 같은 이야기가 화면 어디에도 없습니다. 심사원의 첫 질문이 "그 폰 분실하면요?"일 겁니다.
7. **01-main.png 배터리 최적화 배너**: 필요한 안내인 건 알겠는데, 이게 꺼져 있지 않으면 "백업이 조용히 멈출 수 있다"는 뜻이죠. 그렇다면 배너로 끝낼 게 아니라, 멈췄을 때 그 사실이 기록되고 알림이 와야 합니다. 10-settings.png의 "부팅 후 서버 자동 시작"이 기본으로 꺼져 있는 것도 백업 용도에서는 반대가 맞습니다.
8. **"서버"와 "백업"이 섞여 있습니다.** 01-main.png 맨 위가 "서버 켜짐 + IP"입니다. 저한테 중요한 건 서버가 아니라 미러 상태입니다. 서버를 꺼도 미러는 계속 따라가는지 헷갈립니다.
9. **이슈·PR·위키**: 화면 어디에도 없습니다. 코드만 지킨다는 걸 명확히 써 주면 오히려 괜찮습니다. 애매하게 두면 감사 문서에 잘못 적게 됩니다.
10. **LFS·서브모듈**: 03-add-mirror.png의 "고급" 아래에 있는지 모르겠지만, 포함 여부가 등록 정보에 보였으면 합니다.

### 저와는 상관없는 부분

- 09-qr.png: 개발자 노트북에 주소 넘길 일이 거의 없어서 쓸 일 없습니다.
- 12-launcher-icon.png, 13-main-dark.png, 18-web-repo-home-dark.png: 깔끔합니다. 그 이상의 의견은 없습니다.

## 4. 비교·참고할 만한 제품

| 제품 | 좋은 점 | 아쉬운 점 |
|---|---|---|
| **직접 짠 스크립트 + NAS + S3** (지금 쓰는 것) | 싸고, 원하는 대로 고칠 수 있음 | 실패 알림 없음, 만든 사람(저)만 고칠 수 있음, 감사 증적은 수작업 |
| **Rewind Backups for GitHub (구 BackHub)** | 이슈·PR·위키까지 백업, 복구 버튼, 감사 보고서 기능. 심사원이 이름을 알아서 설명이 쉬움 | 레포·사용자 수 기반 구독이라 6명 회사에는 비쌈. 백업이 또 다른 SaaS에 있다는 게 "GitHub가 막히면?" 질문에 대한 완전한 답은 아님 |
| **GitProtect.io 등 상용 DevOps 백업** | 스케줄, 보존 정책, 암호화, 저장 위치 선택, 리포트 | 기능이 너무 많고 엔터프라이즈 가격·영업 위주. 설정 화면이 무거움 |
| **Gitea / Forgejo 자체 호스팅 pull mirror** | 무료, 미러 주기 설정, 웹 UI, 사람별 계정·권한 | 서버를 하나 더 운영해야 함. force-push·원본 삭제 시 이전 기록 보존은 기본으로 안 됨. 업데이트·보안 패치가 또 내 일 |
| **gickup, ghorg 같은 오픈소스 CLI** | Org 전체를 한 번에, 여러 목적지(로컬, S3, 다른 git 호스트)로. 설정 파일 하나 | 결국 cron·알림·모니터링은 직접 붙여야 함. 지금 제 스크립트와 고민이 같음 |
| **GitLab 쪽 pull mirroring** | 다른 호스트에 실시간 사본 | 유료 플랜 기능이고, GitLab을 하나 더 쓰는 비용 |
| **GitHub Org 마이그레이션 export** | 공식, 메타데이터까지 포함 | 수동, 느림, 자동화하려면 또 스크립트 |
| **AWS CodeCommit 같은 클라우드 git 저장소** | 다른 클라우드에 두 번째 원격 | 한동안 신규 가입을 막는 등 서비스 존속이 불안했던 기억이 있어서 재해 대비 용도로 믿기 어려움 |

mobilegit이 이들 사이에서 가질 수 있는 자리는 **"구독료 없음 + 서버 운영 없음 + 물리적으로 GitHub·클라우드와 완전히 분리된 사본"**입니다. 감사에서 "GitHub와 클라우드 계정이 동시에 막혀도 사무실 서랍 안 기기에 사본이 있다"는 말은 꽤 설득력이 있습니다. 다만 그러려면 위에 적은 운영·보안 기능이 받쳐 줘야 합니다.

## 5. 꼭 더해졌으면 하는 것 3가지와 없어도 되는 것

### 꼭 더해졌으면 하는 것

1. **조용한 실패를 없애는 상태판과 알림**
   - 메인 맨 위에 "정상 N / 실패 N / 마지막 전체 성공 시각"
   - 실패, 토큰 만료 임박(D-14), N일 이상 미동기화, 저장 공간 부족 시 알림 (폰 알림 + 가능하면 이메일이나 Slack 웹훅)
   - Org 단위 "계속 따라가기": 새 레포 자동 포함, 원본 삭제·아카이브 시 사본은 보존하고 표시만
2. **감사 증적 내보내기 + 무결성 검사**
   - 주기적 `git fsck` 자동 실행과 결과 기록

- **PC 프로젝트 올리기 / 빈 레포 만들기 (02, 04)**: 회사 용도에서는 GitHub 밖에 원본이 생기는 걸 원치 않습니다.

## 6. 그 외에 하고 싶은 말

- **폰 한 대 = 단일 장애점**이라는 걸 앱이 먼저 인정해 주면 좋겠습니다. 저는 이걸 "3-2-1 백업에서 GitHub와 S3 외의 세 번째, 물리적으로 분리된 사본"으로 쓰고 싶습니다. 사무실에 남는 구형 안드로이드폰 하나를 충전기에 꽂아 서랍에 두는 그림입니다. 이 용도를 염두에 둔 "상시 거치 모드"(화면 꺼짐 유지, 부팅 자동 시작 기본 켬, 충전 중일 때만 큰 동기화, 발열 관리)가 있으면 딱 맞을 것 같습니다.
- 개인 폰에 회사 코드 전체를 넣는 건 저도 직원도 원하지 않습니다. 회사 소유 기기 하나에 두는 걸 전제로 설계해 주시면 됩니다.
- **가격**: 사람 수 기반 구독이면 안 씁니다. 그럴 거면 Rewind를 씁니다. 한 번 사는 앱이나, 기기 한 대당 연 몇만 원 수준이면 "스크립트 유지보수 시간 아끼는 값"으로 바로 결제합니다. 감사 리포트 기능은 유료로 분리해도 냅니다.
- 마지막으로, 복구가 백업보다 중요합니다. "GitHub가 사라졌다고 치고, 이 폰에서 새 GitHub Org(또는 GitLab)로 레포 전체를 되돌려 push하기" 같은 **복구 마법사**가 있으면, 그 화면 캡처 하나가 감사 때 제일 강한 증거가 될 겁니다.
