# 인터뷰 02 — 임베디드·IoT 펌웨어 엔지니어 (11년 차)

- 일하는 곳: 공장 설비 제어기, 발전소 보조설비 모니터링 장비 펌웨어. MCU는 STM32, ESP32, 일부 NXP i.MX RT
- 쓰는 도구: 회사 사내 GitLab(자체 호스팅, 사설 인증서, VPN 안에서만 접속), VS Code + PlatformIO, STM32CubeIDE, J-Link/ST-Link, 시리얼 터미널(Tera Term), 출장용 노트북 1대, 업무폰(안드로이드)
- 출장: 한 달에 1~3번. 짧으면 하루, 길면 2주 상주
- 확인한 화면: 01~18 전부

## 1. 현장 출장에서 코드를 가져가고, 고치고, 다시 들여오는 실제 흐름

### 출발 전 (회사, 사내망)
1. 사내 GitLab에서 해당 현장 프로젝트를 노트북에 clone하거나 pull합니다. 서브모듈(벤더 SDK, 공통 HAL, 프로토콜 스택)이 3~5개 걸려 있어서 `git submodule update --init --recursive`까지 꼭 해 둬야 합니다. 이걸 깜빡하고 현장에서 빌드가 안 돼서 반나절 날린 적이 있습니다.
2. 현장에 지금 깔려 있는 펌웨어 버전이 어느 태그인지 확인합니다. 사실 이게 제일 불확실합니다. 납품 이후 다른 사람이 현장에서 고친 버전이 깔려 있는 경우가 꽤 있습니다.
3. 혹시 몰라 `git bundle create proj.bundle --all`로 번들을 만들어 USB에 하나 더 넣어 갑니다. 노트북이 고장 나거나 보안 검색에서 노트북 반입이 막히는 경우를 대비해서입니다.
4. 빌드된 .bin/.hex도 버전별로 폴더에 담아 갑니다. 롤백용입니다.

### 현장 (폐쇄망)
5. 보안 검색을 거칩니다. 발전소는 노트북과 USB를 등록하고 봉인 스티커를 붙입니다. 폰은 카메라에 스티커를 붙이고 들고 들어갈 수 있는 곳과, 아예 사물함에 맡기는 곳이 반반쯤 됩니다. 공장은 대체로 폰은 됩니다.
6. 노트북은 장비 제어망에 유선으로 붙거나 디버거만 연결하고, 인터넷은 당연히 안 됩니다. 현장 와이파이는 없거나 써서는 안 되는 것이 대부분입니다.
7. 장비 옆에서 고치고, 빌드하고, 굽고, 확인합니다. 한 번에 고쳐지는 일은 드물어서 하루에 커밋이 10~20개씩 생깁니다. 그런데 정신없을 때는 커밋도 안 하고 그냥 고치다가 나중에 정리합니다.
8. 어느 장비(시리얼 번호)에 어느 빌드를 구웠는지는 수첩에 손으로 적거나, 메모장 파일에 적습니다. 장비가 20대쯤 되면 이게 제일 헷갈립니다.

### 복귀 후 (회사)
9. 노트북을 사내망에 붙이고 브랜치를 만들어 push하는 게 원칙입니다. 그런데 출장 노트북이 사내망 접속 승인이 안 된 장비거나, 복귀 직후 다른 현장으로 바로 가야 하면 며칠씩 미뤄집니다.
10. 그래서 실제로는 `git format-patch`로 패치를 뽑아 USB로 옮기거나, 번들을 만들어 사무실 PC에서 `git fetch`로 받습니다. 사무실 PC는 USB 저장장치가 DLP(보안 솔루션)로 막혀 있어서, 보안팀에 반입 신청을 하고 하루 기다린 적도 있습니다.
11. 최악의 경우는 메모장에 "main.c 342행 타임아웃 500→1500"처럼 적어 와서 손으로 다시 고치는 겁니다. 11년 동안 이렇게 해서 빠뜨린 수정 때문에 같은 현장에 다시 간 적이 두 번 있습니다.
12. MR을 올리고 리뷰를 받은 뒤 머지하고, 현장 배포 버전에 태그를 붙입니다. 이 태그를 잊으면 다음 출장 때 2번 문제가 그대로 되풀이됩니다.

## 2. 단계별 불편한 점과 있었으면 하는 기능

| 단계 | 불편한 점 | 있었으면 하는 기능 |
|---|---|---|
| 출발 전 준비 | 서브모듈을 빠뜨림. 사내 GitLab은 사설 인증서라 일반 도구에서 SSL 오류가 남. 어느 태그가 현장에 깔려 있는지 모름 | 서브모듈까지 한꺼번에 미러, 사설 CA 인증서 등록, "출장 전 최신 동기화 완료" 표시 |
| 현장 작업 | 노트북 한 대에만 작업이 있어 노트북이 죽으면 끝. 인터넷이 없어 백업할 곳이 없음 | 폰을 USB 테더링이나 핫스팟으로 붙여서 그냥 `git push phone`으로 백업. 와이파이 공유기가 없는 상태가 기본이라는 전제 |
| 장비별 기록 | 어떤 장비에 어떤 빌드를 올렸는지 수첩에 적음 | 커밋이나 태그에 장비 시리얼과 메모를 붙이는 기능, 또는 빌드 산출물(.bin) 보관 |
| 회사로 반입 | USB가 막혀 있음. 패치를 옮기다 빠뜨림. 출장 노트북이 사내망에 못 붙음 | 폰이 사내 GitLab에 다시 닿으면 현장 브랜치를 원본으로 push해 주는 기능 |
| 정리 | 현장에서 한 커밋이 지저분하고 태그를 잊음 | 반입 전에 "원본에 없는 커밋 목록"을 보여 주는 화면 |

핵심은 하나입니다. **제가 원하는 건 "원본을 따라가는 미러"와 "제가 고친 걸 받아 주는 저장소"가 한 레포 안에 같이 있는 것**입니다. 출발 전에는 회사 것을 미러로 받고, 현장에서는 거기에 push하고, 돌아오면 그 차이를 회사로 돌려보내는 것. 이게 한 바퀴 돌아야 제 일에 쓸 수 있습니다.

## 3. 스크린샷이 제 작업 흐름에 맞는가

### 바로 쓸 수 있을 것 같은 부분
- **04-pc-upload-guide**: `git remote add phone ...`, `git push -u phone main` 두 줄을 복사하게 해 준 것 아주 좋습니다. 현장에서 정신없을 때 명령어를 기억할 필요가 없습니다. remote 이름을 `phone`으로 정해 준 것도 마음에 듭니다.
- **07-repo-detail-local**의 "내보내기 — git bundle 또는 소스 zip": 제가 지금 손으로 하는 일 그대로입니다. 번들이 폰에서 바로 나오면 USB 반입 절차가 필요한 곳에서도 쓸 수 있습니다.
- **08-push-history**: 언제, 어느 IP에서, 어느 브랜치가 어디서 어디로 바뀌었는지 남는 게 좋습니다. 현장에서 노트북 두 대로 같이 작업할 때 누가 덮어썼는지 따질 수 있습니다. "새로 만듦" 배지도 알아보기 쉽습니다.
- **10-settings**의 "연결 경로별 보안": 와이파이는 암호화가 안 된다고 솔직하게 써 둔 게 신뢰가 갑니다. 보안팀에 설명할 때도 이 문장을 그대로 쓸 수 있겠습니다.
- **11-storage**: 남은 공간 1GB 아래에서 자동 업데이트를 멈추는 것은 현장에 맞습니다. 벤더 SDK가 커서 용량을 신경 써야 합니다.
- **16-web-file-view**, **17-web-commit-log**: 노트북 하나로 작업하는 동안 동료가 자기 노트북 브라우저로 코드를 같이 보는 데 쓸 수 있겠습니다. 줄 번호와 "파일 다운로드"가 있는 것도 좋습니다.

### 빠져 있거나 헷갈리는 부분
1. **06-repo-detail-mirror의 "분리하기"가 제 흐름을 끊습니다.** 회사 레포를 미러로 받아 갔는데, 현장에서 push하려면 분리해야 한다고 나옵니다. 분리하면 원본을 더 이상 따라가지 않는 것으로 읽히는데, 그러면 돌아와서 회사로 돌려보낼 길도 없어지는 것 아닌가요? 저는 main은 미러로 계속 따라가고, `field/*` 같은 브랜치만 push를 받아 주는 방식을 원합니다. 지금 화면에서는 "분리"하면 무엇을 잃는지 알 수 없어서 누르기 무섭습니다.
2. **원본으로 되돌려 보내는 기능(upstream push)이 없습니다.** 앱 전체를 봐도 "받는" 방향뿐입니다. 제게는 돌아와서 회사 GitLab으로 "보내는" 방향이 더 중요합니다.
3. **01-main, 10-settings에 "인터넷도 와이파이 공유기도 없는 경우"가 없습니다.** 설정에는 와이파이, Tailscale, ngrok 세 가지만 있습니다. 제 현장에는 셋 다 없습니다. 쓸 수 있는 것은 폰 핫스팟에 노트북을 붙이거나 USB 테더링뿐입니다. 이때 01-main의 주소 `192.168.31.120`이 핫스팟 주소로 바뀌는지, USB 테더링 주소도 보여 주는지 알 수 없습니다. "핫스팟/USB 테더링으로 연결" 항목이 따로 있으면 좋겠습니다. 다만 폰 핫스팟 자체가 금지된 현장도 있어서, USB 케이블 연결이 가장 확실합니다.
4. **03-add-mirror에 사내 GitLab 설정이 보이지 않습니다.** "원본 접속 토큰"은 있는데 사설 인증서(자체 CA)를 받아 줄 수 있는지, SSH 주소(`git@gitlab.사내:group/proj.git`)를 넣어도 되는지 알 수 없습니다. "고급"을 열면 있을지도 모르겠지만, 접혀 있어서 모릅니다. 서브모듈을 같이 받는지도 표시가 없습니다. "PR 브랜치 34개 제외"처럼 친절하게 알려 주는 걸 보면 "서브모듈 3개 함께 받기"도 여기 들어가면 딱 맞습니다.
5. **17-web-commit-log에서 diff를 볼 수 있는지 모르겠습니다.** "파일 보기"만 있고, 그 커밋에서 무엇이 바뀌었는지를 보는 버튼이 안 보입니다. 현장에서 동료와 "어제 내가 바꾼 거 뭐였지?"를 볼 때 diff가 제일 필요합니다.
6. **15-web-repo-home 상단 "웹에서는 보기만 할 수 있어요"**: 이건 맞는 판단이라고 생각합니다. 다만 "보존된 기록 0개"(15 오른쪽 정보 패널)가 무엇을 뜻하는지 바로 와닿지 않습니다. 원본에서 force-push로 사라진 커밋을 여기서 보여 준다는 뜻이라면, 우리 회사처럼 누가 현장 브랜치를 rebase로 날려 버리는 일이 있을 때 정말 귀한 기능입니다. 그런데 이름만으로는 짐작이 안 됩니다.
7. **비밀번호가 하나뿐입니다(04, 06, 10).** 현장에서 협력사 직원 노트북이 와이파이에 같이 붙어 있을 때가 있습니다. 그 사람에게 읽기만 허용하고 push는 못 하게 하려면 레포별 또는 사용자별 권한이 필요합니다. 10의 "push만" 옵션은 반대 방향(읽기는 열고 push만 막기)이라 제 경우에 맞지 않습니다.
8. **폰 분실 대비가 안 보입니다.** 회사 소스가 폰에 들어가는 순간 보안팀이 가장 먼저 물어볼 것은 "폰 잃어버리면?"입니다. 앱 잠금(지문)이나 저장소 암호화 여부를 한 줄이라도 보여 주면 승인을 받기 훨씬 쉬워집니다.
9. **01-main의 배터리 최적화 배너**: 내용은 필요한데, 현장에서는 폰을 하루 종일 충전기에 꽂아 두고 노트북에 USB로 붙여 둡니다. 화면이 꺼져도 서버가 안 죽는 것만 보장되면 됩니다.
10. **09-qr**: 노트북에는 카메라로 찍을 일이 없어서 저는 거의 안 쓸 것 같습니다. 다른 폰이나 태블릿으로 볼 때만 쓸모가 있겠습니다.

## 4. 비교하거나 참고할 만한 제품

| 제품 | 좋은 점 | 아쉬운 점 |
|---|---|---|
| **git bundle + USB** (지금 주로 쓰는 방법) | 도구가 따로 필요 없음. 파일 하나라 반입 신청이 쉬움 | USB가 DLP로 막힌 곳이 많음. 어느 번들이 최신인지 헷갈림. 받는 쪽에서 명령을 기억해야 함 |
| **USB 메모리 안의 bare 레포** (`git init --bare`) | 노트북에서 그냥 remote로 씀 | 바이러스 검사와 봉인 절차 때문에 쓸 때마다 번거로움. 파일시스템이 깨지면 끝 |
| **Gitea / Forgejo를 라즈베리파이나 미니 PC에 설치** | 웹 화면, 권한, 미러, diff 모두 됨 | 장비를 하나 더 들고 다녀야 하고, 전원과 반입 등록이 또 필요함. 출장 짐이 늘어남 |
| **Termux + git (+ git daemon / sshd)** | 폰을 서버로 쓰는 것 자체는 지금도 됨 | 설정이 손에 익지 않으면 현장에서 못 씀. 백그라운드에서 죽음. 동료에게 권할 수 없음 |
| **MGit (안드로이드)** | 폰에서 clone/pull 가능 | 클라이언트일 뿐이라 노트북이 push할 수 없음 |
| **Fossil SCM** | 파일 하나에 웹 화면, 티켓, 위키까지 있어서 오프라인 현장에 의외로 잘 맞음 | 회사가 git을 쓰니 변환이 필요하고 팀이 안 따라옴 |
| **GitLab 자체 기능(Push/Pull mirror, Geo)** | 공식 지원 | 사내망 서버끼리만 의미가 있음. 현장 폐쇄망과는 상관없음 |
| **Syncthing** | 폴더 동기화가 아주 편함 | `.git` 폴더를 동기화하다 깨진 경험이 있음. git을 이해하는 도구가 아님 |

mobilegit이 위 표에서 비어 있는 자리, 즉 "따로 장비를 들고 가지 않아도 되는 Gitea"를 채워 줄 수 있다면 저는 씁니다.

## 5. 꼭 더해졌으면 하는 것 3가지, 없어도 되는 것

### 꼭 더해졌으면 하는 것
1. **미러에 "현장 브랜치" push 허용 + 원본으로 되돌려 보내기**
   main 등 원본 브랜치는 읽기 전용 미러로 두고, `field/*` 같은 정해진 브랜치만 push를 받는다. 폰이 다시 사내 GitLab에 닿으면 "원본에 없는 커밋 N개"를 보여 주고 버튼 하나로 원본에 push한다(MR까지 만들어 주면 더 좋음). 06의 "분리하기"를 대신하는 기능.
2. **인터넷과 공유기가 없는 연결: USB 테더링 / 핫스팟 모드**
   01-main과 10-settings에 이 연결을 정식 경로로 넣고, 그때의 주소를 04 명령어에 바로 반영. 현장에서는 이게 기본 경로입니다.
3. **사내 GitLab 대응: 사설 CA 인증서, SSH 주소, 서브모듈 함께 미러**
   03-add-mirror에서 이게 안 되면 출발 전 준비 단계부터 막힙니다.

(4번을 꼽는다면 커밋이나 태그에 장비 시리얼·현장명 메모 붙이기와 .bin 같은 빌드 산출물 보관입니다.)

### 없어도 되는 것
- **ngrok (10-settings "밖에서 접속하기")**: 저희 회사에서는 회사 소스를 외부 터널로 여는 순간 보안 사고입니다. 오히려 기본으로 꺼 두고 숨겨 두는 게 좋겠습니다. 사내 정책상 앱 승인을 받을 때도 "외부 노출 기능 없음"이 유리합니다.
- **05-bulk-mirror (계정·조직 일괄 미러)**: 오픈소스를 모으는 사람에게는 좋겠지만, 저는 출장마다 레포 2~3개만 받아 갑니다. 있어도 상관은 없지만 우선순위는 낮습니다.
- **09-qr**: 노트북 위주라 거의 안 쓸 것 같습니다.
- **다크 모드(13, 18)**: 있으면 좋지만 없어도 됩니다. 다만 발전소 제어실은 어두운 경우가 많아서, 이미 만들었다면 남겨 두세요.

## 6. 그 외에 하고 싶은 말

- 11년 동안 이 문제를 "원래 그런 것"으로 여기고 USB와 수첩으로 버텼습니다. 폰은 어차피 현장에 들고 가는 물건이라 짐이 늘지 않는다는 점이 이 앱의 가장 큰 장점입니다. 장비를 하나 더 들고 가라고 하면 안 씁니다.
- 다만 제 업계에서 이 앱을 쓰려면 기능보다 **보안팀 승인**이 먼저입니다. 데이터가 폰 밖으로 어디에도 안 나간다는 것, 외부 터널을 끌 수 있다는 것, 분실 시 대책을 한 페이지로 정리해 주면 도입이 훨씬 쉬워집니다. 10-settings의 "연결 경로별 보안"처럼 솔직하게 쓴 문장이 그 한 페이지의 시작이 될 수 있다고 봅니다.
- 그리고 현장에 따라 폰 반입 자체가 안 되는 곳도 있다는 점은 알고 계셨으면 합니다. 그런 곳에서는 07의 git bundle 내보내기, 그리고 반대로 **번들 가져오기(노트북에서 만든 번들을 폰에 넣어 레포로 받기)**가 유일한 길입니다. 내보내기만 있고 가져오기가 없는 것 같아 아쉽습니다.
- 08-push-history를 보면서 든 생각인데, 현장에서는 "언제 누가 push했나"보다 "이 커밋을 어느 장비에 구웠나"가 더 중요합니다. 이 화면에 메모 한 줄만 달 수 있어도 제 수첩은 은퇴할 수 있을 것 같습니다.
